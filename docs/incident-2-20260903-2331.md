# Incident 2 — 2026-09-03 ~23:31 ("overheat" episode)

Collection: [incidents/20260903-233942](../incidents/20260903-233942/). First
incident with the full discriminator suite armed. Loggers stopped 23:31:36;
per the user this is most likely the manual power cut, so the stop itself is
treated as non-evidence. EC uptime shows the EC never rebooted; AP resets at
~23:32 (first, still-borked boot) and ~23:37 (clean boot).

## Question under test

Did the **NVIDIA driver initiate** a cascading failure into the PD/EC
controllers and CPU/GPU/EC thermal limits?

## Driver-side instruments — nothing

- **NVML (5s cadence):** flags only 0x0/0x4 (idle) the whole session — no SW
  thermal slowdown, no HW slowdown, no power cap; P0 with normal clocks/power
  (~88W, 76-82°C) to the final sample. Cleaner than incident 1.
- **DxgKrnl Operational/Admin:** zero events in the incident window (only
  routine event-455 clusters at boots). No TDR, no preemption timeouts, no
  engine resets. System log: no 4101/nvlddmkm.
- **Split-brain heartbeat:** both loggers stopped together at the power cut —
  no differential signal either way (discounted per user).

## Verdict for the driver-initiation hypothesis (this incident)

Both driver-boundary instruments (NVML and Microsoft's DxgKrnl scheduler
layer above the closed driver) show **no driver anomaly preceding anything**.
The observable initiators are, in order: thermal soak on board sensors →
soft thermal throttle, with **EC↔SMU (SB-RMI) mailbox failures occurring
during the load window before the throttle** — the first incident where the
mailbox misbehaved in-window, strengthening the Fable 5.1 structural thesis.
The driver's demonstrated contribution is generating the load/heat.

**Known blind spot (keeps the hypothesis alive):** the driver can talk to the
EC through NVAPI/ACPI D-notify (dGPU power tiers, memmap 0x197
`DGPU_DX_STATUS`) which neither NVML, DxgKrnl, nor the EC console logs on
change. A driver-initiated D-notify transition at the wrong moment remains
unobservable with current instruments; reading 0x197 requires either an EC
console (`cpupower`) or a memmap path framework_tool doesn't expose.

## New hypothesis (user): near-full charge-avoidance logic under high load

Both incidents spent their whole session in the same odd charge state:
**battery at/near 100%, "not accepting current" (charger idle), yet
continuously discharging 3-5.5W in battery-assist** with AC connected — i.e.
parked exactly on the full/not-full boundary of the EC's charge state
machine (`calc_is_full()` hysteresis + sustainer in `battery_extender.c`,
default window 100/100).

Correlation with event timing:
- **Incident 2:** battery stepped 100→99% at 23:22:19 and **99→98% at
  23:30:57 — ~40s before the event/power cut**; earlier state flip
  "to full" → "to empty" at ~22:54.
- **Incident 1:** battery still read 100% at ~21:44; the two
  `EC_HOST_EVENT_BATT_BTP` events (21:39:45, 21:56:51) are precisely
  battery-level trip-point crossings, freeze at 22:01:33.

Mechanism candidates: when SoC finally drops enough to flip `is_full`,
`charge_request()` re-enables charging — reprogramming the BQ25770
(charge/input current, possibly discharge-on-AC/learn transitions) while the
system is pulling ~200W through the 48V EPR contract; and/or the host-side
BTP notification makes Windows/AMD PMF re-arbitrate AC-vs-DC power tables
mid-load (note the PMF sPPT difference: 45000mW in-session vs 54000mW at
boot). Either path puts a charger/power-policy mode transition at the worst
possible moment.

**Decisive, reversible experiment:** set a battery charge limit of ~80%
(BIOS or `framework_tool --charge-limit 80` — user-applied). That parks the
sustainer at 75-80%, gives the battery real headroom, and removes the
full-boundary logic from gaming sessions entirely. If incidents stop, the
near-full state machine is implicated; combine with the side-port (SPR-only)
charging experiment to separate it from the EPR variable.
